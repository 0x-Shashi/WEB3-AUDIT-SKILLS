# Formal Verification Proof Strength Evaluation

## Overview

Formal verification proofs can range from genuinely STRONG (universal symbolic
coverage of all branches) to effectively VACUOUS (trivially true due to
contradictory assumptions). This methodology provides a systematic 6-point
analysis to classify each proof harness and identify weaknesses.

### Why This Matters for Auditors

When reviewing a codebase that claims formal verification:
- **92% of reported "formally verified" contracts still have bugs** — the proofs
  don't cover the right properties
- Proofs with concrete inputs are **unit tests**, not formal proofs
- Proofs with contradictory assumptions are **vacuously true** — they prove nothing
- Proofs with symbolic inputs that collapse to a narrow range have **reduced coverage**

This methodology turns "we have 100 proofs" into actionable quality metrics.

### Scope

This methodology applies to:
- **Kani** (Rust, used by Solana programs)
- **Certora** (Solidity, EVM protocols)
- **Halmos** (Solidity, symbolic EVM execution)
- **KEVM** (K framework for EVM)
- **Move Prover** (Move language, Aptos/Sui)
- **Any bounded model checker** or symbolic execution tool

## The 6-Point Analysis

### Point 1: Input Classification

For each proof harness, classify every input to the function-under-test:

| Classification | Definition | Verification Strength |
|----------------|------------|----------------------|
| **Symbolic** | Generated by solver (`kani::any()`, Certora `env`, Halmos symbolic) | Strong — explores all possible values |
| **Concrete** | Hardcoded value | Weak — single execution path |
| **Derived** | Computed from other inputs | Depends on source inputs |
| **Bounded Symbolic** | Symbolic with `assume`/`require` constraints | Medium — see Point 5 |

**Critical rule**: A proof where ALL function inputs are concrete is a **unit test**,
not a formal proof. It tests one execution path, not a property.

#### Tool-Specific Patterns

**Kani (Rust)**:
```rust
// SYMBOLIC — strong
let x: u64 = kani::any();

// BOUNDED SYMBOLIC — check bounds
let x: u64 = kani::any();
kani::assume(x > 0 && x < 1000);

// CONCRETE — unit test input
let x: u64 = 42;
```

**Certora (Solidity)**:
```cvl
// SYMBOLIC — strong
env e;
uint256 amount;
deposit(e, amount);

// BOUNDED — check requirements
require amount > 0 && amount < totalSupply();

// CONCRETE — weak
require amount == 1000;
```

**Halmos (Solidity)**:
```python
# SYMBOLIC — strong
amount = halmos.uint256("amount")

# BOUNDED — check bounds
halmos.assume(amount > 0)

# CONCRETE — unit test
amount = 1000
```

### Point 2: Branch Coverage Analysis

Read the function-under-test and list every conditional branch:

| Branch Type | Examples | What to Check |
|-------------|----------|---------------|
| `if`/`else` | `if (x > threshold)` | Can solver reach both sides? |
| `match` arms | `match result { Ok(_) => ..., Err(_) => ... }` | Are all arms reachable? |
| Short-circuit | `a && b`, `a \|\| b` | Is `b` ever evaluated? |
| Min/Max | `.min()`, `.max()`, `.clamp()` | Both paths of comparison exercised? |
| Saturating ops | `saturating_add`, `saturating_sub` | Overflow path reachable? |
| Checked ops | `checked_mul`, `checked_div` | `None` path reachable? |
| Option/Result | `.unwrap_or()`, `?` operator | Both `Some`/`None` reachable? |

**For each branch**: Determine whether the proof's input constraints ALLOW the
solver to reach both sides. A proof that only exercises one side of a critical
branch is weaker than it appears.

#### Example Analysis

```rust
fn decide_trade(
    shape_ok: bool,    // gate 1
    auth_ok: bool,     // gate 2
    gate_active: bool, // gate 3
    risk_increase: bool // gate 4
) -> Decision {
    if !shape_ok { return Reject; }        // branch A
    if !auth_ok { return Reject; }         // branch B
    if gate_active && risk_increase {       // branch C
        return Reject;
    }
    Accept                                  // branch D
}
```

A proof with `shape_ok = true` (concrete) can never reach branch A.
A proof with symbolic `shape_ok` but concrete `auth_ok = false` always exits at B,
never reaching branches C or D.

### Point 3: Invariant Strength

Classify what the proof actually asserts:

| Assertion Type | Strength | Description |
|----------------|----------|-------------|
| **Universal characterization** | Highest | Output == exact formula for ALL inputs |
| **Property** | High | Invariant holds (monotonicity, conservation, bounds) |
| **Rejection proof** | High | Bad input → always rejected |
| **Acceptance proof** | Medium | Good input → always accepted |
| **Code-equals-spec** | Low | Assert restates the function body |
| **No assertion** | None | Proof only checks for panics/overflows |

**Universal characterization** is the gold standard — it proves that a function's
output is EXACTLY a specific formula for every possible input combination:

```rust
// UNIVERSAL: Proves exact behavior for all 2^4 = 16 input combinations
#[kani::proof]
fn trade_universal() {
    let (shape, auth, gate, risk) = (kani::any(), kani::any(), kani::any(), kani::any());
    let result = decide_trade(shape, auth, gate, risk);
    assert!(result == Accept <==> (shape && auth && !(gate && risk)));
}
```

**Code-equals-spec** is low value — the assertion just restates the function body:

```rust
// WEAK: Asserts the function does what it does
fn accumulate_dust(a: u64, b: u64) -> u64 { a.saturating_add(b) }

#[kani::proof]
fn dust_test() {
    let (a, b) = (kani::any(), kani::any());
    assert!(accumulate_dust(a, b) == a.saturating_add(b)); // tautological
}
```

### Point 4: Vacuity Risk Assessment

A proof is **vacuous** if its assertions are trivially true because they are
never reached. Watch for:

#### 4a. Contradictory Assumptions

```rust
kani::assume(x > 100);
kani::assume(x < 50);  // CONTRADICTION — no valid x exists
// All subsequent assertions are trivially true
```

#### 4b. Unreachable Assertions

```rust
let result = decide_trade(shape, auth, gate, risk);
if result == Accept {
    assert!(nonce_new == nonce_old + 1);  // Only checked if Accept
}
// If solver always chooses Reject path, assertion is never checked = VACUOUS
```

**Mitigation**: Non-vacuity witnesses — concrete examples proving both paths
are reachable:

```rust
// NON-VACUITY WITNESS: Prove Accept is reachable
debug_assert!(decide_trade(true, true, false, false) == Accept);

// Now the universal proof is non-vacuous
let result = decide_trade(kani::any(), kani::any(), kani::any(), kani::any());
match result {
    Accept => assert!(nonce_new == nonce_old + 1),
    Reject => assert!(nonce_new == nonce_old),
}
```

#### 4c. Single-Path Assumptions

```rust
let x: u64 = kani::any();
kani::assume(x == 42);  // Collapses symbolic to concrete
// This is a unit test disguised as a proof
```

### Point 5: Symbolic Collapse Detection

Even with `kani::any()`, derived values can collapse the symbolic range:

#### 5a. SAT-Bounded Domains

Division and multiplication chains create exponential SAT blowup. Proofs often
bound inputs to keep verification tractable:

```rust
const MAX_SCALE: u64 = 64;  // Real range: 0..u32::MAX
let scale: u64 = kani::any();
kani::assume(scale > 0 && scale <= MAX_SCALE);
```

**Evaluate**: Is the bounded domain sufficient to exercise all branches?
If `scale == 0` is a special case with its own branch, and the proof excludes it,
that branch is uncovered.

#### 5b. Derived Value Collapse

```rust
let price: u64 = kani::any();
let scale: u64 = kani::any();
kani::assume(scale > 0 && scale <= 64);
let scaled = price * 1_000_000 / scale;
// If price is small and scale is large, scaled might always be 0
// This locks the "zero result" branch and never exercises "non-zero result"
```

#### 5c. Forced-Path Collapse

```rust
// "Universal" proof that forces one gate to fail
kani::assume(!shape_ok);  // Gate 1 always fails
// Other gates (auth, risk) are symbolic BUT never reached
// The proof only tests gate 1 rejection
```

### Point 6: Coupling Completeness

For extracted verification functions (common pattern where pure logic is extracted
from side-effectful handlers):

```
Production Handler         Verification Function
┌──────────────┐          ┌──────────────────┐
│ read accounts │ ───────→ │ decide_trade(    │
│ validate CPI  │          │   shape_ok,      │
│ check auth    │          │   auth_ok,       │
│ execute trade │          │   gate_active,   │
│ update state  │          │   risk_increase  │
└──────────────┘          │ )                │
                          └──────────────────┘
```

**Verify**:
- [ ] The verification function's parameters map 1:1 to actual account/instruction data
- [ ] No production handler makes a decision NOT captured in the verification function
- [ ] Gate ordering in verification matches production handler's check sequence
- [ ] The extraction is complete — no security-relevant logic left in the handler

**Residual gap**: A mismatch between the production handler and the verification
function means the proofs verify a DIFFERENT policy than what runs in production.

## Classification Output

For each proof, assign one classification:

| Classification | Criteria |
|----------------|----------|
| **STRONG** | Symbolic inputs exercise key branches, appropriate property asserted, non-vacuous |
| **WEAK** | Symbolic inputs but misses branches, weaker assertion, or symbolic collapse reduces coverage |
| **UNIT TEST** | Concrete inputs or single execution path — acceptable if intentional |
| **CODE-EQUALS-SPEC** | Assertion restates the function body; guards regressions only |
| **VACUOUS** | Assertions may never be reached or are trivially true |

### Summary Table Template

```markdown
| Classification | Count | % | Description |
|---|---|---|---|
| STRONG | N | x% | Symbolic, full-branch, non-vacuous |
| WEAK | N | x% | Category A/B/C/D weakness |
| UNIT TEST | N | x% | Intentional concrete guards |
| CODE-EQUALS-SPEC | N | x% | Tautological regression guards |
| VACUOUS | N | x% | Trivially true — CRITICAL |
| **Total** | **N** | **100%** | |
```

### Weakness Categories

| Category | Name | Description |
|----------|------|-------------|
| A | Branch Coverage Gaps | Proof misses one or more branches of the function |
| B | Weak Assertions | Property asserted is weaker than the function guarantees |
| C | SAT-Bounded Collapse | Solver domain is bounded for tractability, reducing coverage |
| D | Trivially True | Assertion is always true regardless of inputs |

## Real-World Example: 110-Proof Kani Suite

From auditing a Solana program's 110 Kani proof harnesses:

### Results

| Classification | Count | % |
|---|---|---|
| STRONG | 91 | 82.7% |
| WEAK | 9 | 8.2% |
| UNIT TEST | 5 | 4.5% |
| CODE-EQUALS-SPEC | 5 | 4.5% |
| VACUOUS | 0 | 0.0% |

### What Made This Suite High-Quality

1. **Universal characterization proofs** (Tier 1): 11 proofs that fully characterize
   function outputs for ALL input combinations
2. **Kill-switch proofs** (Tier 2): 8 proofs showing single gate failure → rejection
   regardless of all other inputs
3. **Non-vacuity discipline**: Concrete witnesses before conditional assertions
4. **Both-outcome matching**: `match &decision { Reject => ..., Accept => ... }`
   instead of `if result == Accept { assert!(...) }`
5. **Explicit SAT bounds documentation**: Every WEAK proof documents WHY the bound
   exists and what companion proofs cover the uncovered range

### What Was Improved During Audit

- Removed 42 redundant unit tests subsumed by universal proofs
- Upgraded 1 WEAK proof to STRONG (made fully symbolic)
- Widened SAT bounds on 5 WEAK proofs (u8 → u16)
- Consolidated 3 single-gate proofs into 1 universal proof
- **Net: 152 → 110 proofs, STRONG% from 60.5% → 82.7%**

### Proof Tier Taxonomy

| Tier | Name | Count | Value |
|------|------|-------|-------|
| 1 | Universal Characterization | 11 | Highest — full behavioral spec |
| 2 | Universal Gate Rejection | 8 | Critical — security kill-switches |
| 3 | Nonce Transition Relations | 6 | Critical — state machine correctness |
| 4 | ABI Validation | 12 | High — external input validation |
| 5 | Authorization | 11 | High — access control |
| 6 | Gate Logic + CPI Size | 7 | Medium — helper function properties |
| 7 | Consistency + Coupling | 8 | Medium — internal agreement |
| 8 | Math + Invariants | 22 | Medium — arithmetic correctness |
| 9 | Result Characterization | 3 | Medium — output completeness |
| 10 | Bug Fix Regression | 3 | Important — prevents regressions |

## Applying to Different Verification Tools

### Certora (EVM)

Map the 6 points to Certora concepts:

| Point | Certora Equivalent |
|-------|-------------------|
| Input Classification | `env e` (symbolic), `require x == 5` (concrete) |
| Branch Coverage | Check all `if`/`else` in Solidity function |
| Invariant Strength | `invariant` vs `rule` vs `assert` |
| Vacuity Risk | `require` contradictions, `lastReverted` always true |
| Symbolic Collapse | `mathint` overflow, loop unrolling bounds |
| Coupling | Spec function vs implementation function |

### Halmos (EVM)

| Point | Halmos Equivalent |
|-------|-------------------|
| Input Classification | `halmos.uint256()` (symbolic), hardcoded (concrete) |
| Branch Coverage | Halmos path exploration limits |
| Invariant Strength | `assert` statements in test |
| Vacuity Risk | `halmos.assume()` contradictions |
| Symbolic Collapse | `--loop` bounds, `--depth` limits |
| Coupling | Foundry test function vs contract function |

### Move Prover (Aptos/Sui)

| Point | Move Prover Equivalent |
|-------|------------------------|
| Input Classification | `spec` function inputs, `aborts_if` conditions |
| Branch Coverage | `ensures` covers all `if`/`else` arms |
| Invariant Strength | `invariant` vs `ensures` vs `aborts_if` |
| Vacuity Risk | Contradictory `requires` + `aborts_if` |
| Symbolic Collapse | Boogie solver timeouts |
| Coupling | `spec` module vs implementation module |

## Auditor Workflow

1. **Inventory**: Count all proof harnesses, list functions-under-test
2. **Classify**: Apply 6-point analysis to each proof
3. **Categorize**: Assign STRONG/WEAK/UNIT TEST/CODE-EQUALS-SPEC/VACUOUS
4. **Summarize**: Generate classification table + weakness categories
5. **Recommend**: Specific improvements for non-STRONG proofs
6. **Verify coupling**: Ensure verification functions match production handlers

### Red Flags

| Red Flag | Severity | Meaning |
|----------|----------|---------|
| All proofs use concrete inputs | Critical | No verification, just testing |
| >50% VACUOUS proofs | Critical | Proof suite is theater |
| No rejection proofs | High | Only happy path verified |
| No non-vacuity witnesses | High | Conditional assertions may be vacuous |
| Coupling gaps documented | Medium | Proofs may verify wrong policy |
| All proofs are CODE-EQUALS-SPEC | Medium | Guards regressions, not properties |
| SAT bounds undocumented | Medium | Unknown coverage gaps |

## Security Review Checklist

- [ ] Count total proof harnesses and classify each
- [ ] Identify all VACUOUS proofs (Critical — immediate attention)
- [ ] Check non-vacuity discipline for conditional assertions
- [ ] Verify SAT bounds are documented and justified
- [ ] Assess coupling between verification and production functions
- [ ] Check for missing rejection proofs (bad input → reject)
- [ ] Verify universal characterization proofs exist for critical functions
- [ ] Look for undocumented unit tests masquerading as formal proofs
- [ ] Evaluate whether CODE-EQUALS-SPEC proofs provide value
- [ ] Check if branch coverage gaps align with known attack vectors
