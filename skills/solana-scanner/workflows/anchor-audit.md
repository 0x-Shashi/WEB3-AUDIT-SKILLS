# Anchor Program Audit Workflow

Structured security audit workflow for programs built with the Anchor framework (the dominant Solana development framework, used by >90% of new projects). Anchor provides declarative account validation via `#[derive(Accounts)]` structs, but many vulnerabilities still arise from missing or incorrect constraints.

---

## Prerequisites

- Anchor version identified (check `Cargo.toml` and `Anchor.toml`)
- Program IDL available (generated by `anchor build`)
- All program modules and dependencies mapped
- Local test environment set up (Anchor test or Solana test validator)

---

## Step 1: Program Structure Mapping

Map the complete program architecture:

```
program/
├── lib.rs           → Program entry point, declare_id!, instruction handlers
├── state.rs         → Account data structures (stored on-chain state)
├── instructions/    → Individual instruction handlers
│   ├── initialize.rs
│   ├── deposit.rs
│   ├── withdraw.rs
│   └── admin.rs
├── errors.rs        → Custom error definitions
└── utils.rs         → Helper functions
```

Document:
- All instruction handlers and their purposes
- All account structs (`#[derive(Accounts)]`)
- All data structs (`#[account]`)
- Cross-program invocations (CPIs)
- PDA seeds used throughout the program

---

## Step 2: Account Validation Audit

**This is the most critical step for Anchor programs.**

For every `#[derive(Accounts)]` struct, audit each account field:

### Constraint Checklist

```rust
#[derive(Accounts)]
pub struct ExampleInstruction<'info> {
    // CHECK 1: Is it mutable when it needs to be?
    #[account(mut)]  // ← Required if this account's data or lamports change
    
    // CHECK 2: Does it validate ownership?
    pub vault: Account<'info, VaultData>,  // ← Account<> checks owner == program_id
    
    // CHECK 3: Does it validate relationship?
    #[account(has_one = authority)]  // ← Checks vault.authority == authority.key()
    
    // CHECK 4: Is PDA correctly derived?
    #[account(seeds = [b"vault", authority.key().as_ref()], bump = vault.bump)]
    
    // CHECK 5: Is signer required?
    pub authority: Signer<'info>,  // ← Verifies this account signed the transaction
    
    // CHECK 6: For init, is space correct?
    #[account(init, payer = authority, space = 8 + VaultData::LEN)]
    
    // CHECK 7: For close, is receiver correct?
    #[account(mut, close = authority)]
}
```

### Red Flags to Look For

| Red Flag | Example | Risk |
|----------|---------|------|
| `AccountInfo` instead of `Account<>` | `pub token_account: AccountInfo<'info>` | No type or owner validation |
| Missing `mut` on modified accounts | `pub vault: Account<'info, Vault>` | Transaction will fail silently or succeed with stale data |
| Missing `has_one` | No relationship validation | Any account of correct type accepted |
| Missing `seeds` on PDA | PDA not verified | User can pass arbitrary account |
| `UncheckedAccount` without `/// CHECK:` comment | `pub oracle: UncheckedAccount<'info>` | Anchor warns, but no validation |
| `init_if_needed` | `#[account(init_if_needed, ...)]` | Reinitialization / front-running risk |
| Missing `constraint` on derived values | No custom constraint | Business logic validation skipped |

## Step 3: Instruction Logic Review

For each instruction handler, review the business logic:

### Common Anchor Instruction Bugs

1. **Insufficient remaining_accounts validation**
   ```rust
   // VULNERABLE: No validation on remaining accounts
   for account in ctx.remaining_accounts {
       // Attacker can inject any account
   }
   ```

2. **Incorrect PDA seeds**
   ```rust
   // VULNERABLE: User-controlled seed component
   #[account(seeds = [user_input.as_bytes()], bump)]
   pub pda: Account<'info, Data>,
   // Attacker controls which PDA resolves
   ```

3. **Missing balance checks after CPI**
   ```rust
   // VULNERABLE: Not verifying balance change after token transfer
   token::transfer(cpi_ctx, amount)?;
   // What if token has transfer fee? actual received < amount
   ```

4. **Arithmetic in production**
   ```rust
   // VULNERABLE: Wraps in release mode (no --debug flag)
   let result = a + b; // Can overflow silently
   
   // SAFE: Use checked math
   let result = a.checked_add(b).ok_or(ErrorCode::MathOverflow)?;
   ```

## Step 4: CPI (Cross-Program Invocation) Analysis

Trace all CPIs and verify:

| Check | What to Verify |
|-------|---------------|
| Target program ID | Is the CPI target a hardcoded known program? |
| Signer seeds | Are PDA signer seeds correct and minimal? |
| Account forwarding | Are the right accounts passed to the CPI? |
| Return data | Is CPI return data validated? |
| Privilege inheritance | Does the CPI inherit more authority than intended? |

### High-Risk CPI Patterns

```rust
// RISKY: CPI to user-provided program
invoke(
    &instruction,
    &[ctx.accounts.user_provided_program.to_account_info()],  // ← Who controls this?
)?;

// SAFE: CPI to hardcoded program
token::transfer(
    CpiContext::new(
        ctx.accounts.token_program.to_account_info(),  // ← Anchor validates this is SPL Token
        Transfer { ... },
    ),
    amount,
)?;
```

## Step 5: PDA Verification

For every PDA in the program:

```
PDA: vault_pda
Seeds: [b"vault", user_pubkey, mint_pubkey]
Bump: stored in vault.bump

Verify:
✓ Seeds are deterministic (no randomness)
✓ Seeds include all necessary identifiers (user + mint = unique per user per token)
✓ Bump is stored on first derivation and reused (not recalculated)
✓ Canonical bump used (Anchor does this by default)
✓ Seeds don't include controllable length-variable data without length prefix
```

### PDA Collision Risk

```rust
// RISKY: Seed collision possible
// PDA for "AB" + "C" == PDA for "A" + "BC" if no separator
seeds = [user_input_1.as_bytes(), user_input_2.as_bytes()]

// SAFE: Fixed-length fields or explicit separator
seeds = [b"vault", user.key().as_ref(), &[mint_index]]
```

## Step 6: Math Review

Solana programs compile to BPF bytecode. In **release mode** (the default for deployed programs), Rust integer arithmetic wraps on overflow instead of panicking.

| Operation | Debug Mode | Release Mode | Safe Alternative |
|-----------|-----------|-------------|-----------------|
| `a + b` | Panics on overflow | **Wraps silently** | `a.checked_add(b)` |
| `a - b` | Panics on underflow | **Wraps silently** | `a.checked_sub(b)` |
| `a * b` | Panics on overflow | **Wraps silently** | `a.checked_mul(b)` |
| `a / b` | Panics on div-by-zero | Panics on div-by-zero | `a.checked_div(b)` |

**Review all arithmetic in the program for checked operations.**

---

## Step 7: State Machine Correctness

If the program has state transitions (e.g., `Created → Active → Closed`):

- Verify all valid state transitions are documented
- Verify invalid transitions are rejected
- Check for race conditions between instructions
- Verify state can't get stuck (no dead-end states)
- Check that state transitions emit events

---

## Step 8: Access Control

| Check | Pattern |
|-------|---------|
| Admin functions | `Signer` + `has_one = admin` or `constraint = authority.key() == ADMIN_PUBKEY` |
| User functions | `Signer` + `has_one = owner` on user-owned accounts |
| Program-only functions | PDA-signed CPI only (no direct user calls) |
| Upgrade authority | Check `anchor_lang::solana_program::bpf_loader_upgradeable` |

---

## Step 9: Token Operations

For all SPL Token interactions:

```
✓ Token account mint validated (correct token type)
✓ Token account authority validated (correct owner)
✓ Transfer amounts checked (no zero-amount transfers)
✓ Associated Token Account used where appropriate
✓ Token-2022 extensions considered (transfer fees, confidential transfers)
✓ Decimal handling correct across different mints
```

---

## Step 10: Report

Structure findings using the Solana-specific severity guide:

| Severity | Criteria | Example |
|----------|----------|---------|
| **Critical** | Direct unauthorized fund theft | Missing signer check on withdraw |
| **High** | Fund loss under specific conditions | Integer overflow in price calculation |
| **Medium** | Incorrect behavior, limited impact | PDA bump not stored (extra compute) |
| **Low** | Best practice violation | Missing error code documentation |
| **Informational** | Suggestion | Could upgrade to Token-2022 |
